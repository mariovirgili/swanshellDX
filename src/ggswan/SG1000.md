# sgswan: the SG-1000 plugin (work in progress)

`PLUG_SG.BIN` is to be built from the ggswan sources with
`-DGGSWAN_SG1000`, the way `PLUG_SMS.BIN` is built with `-DGGSWAN_SMS`.
This file is the plan and the memory map; it is kept up to date as the
steps are done.

runs on the WonderSwan yet: there is no `PLUG_SG.BIN`, and `PLUG_GG.BIN`

## The machine

| | SG-1000 | here |
|---|---|---|
| CPU | Z80, 3.58 MHz | the same core and recompiler as ggswan |
| ROM | 8 to 48 KiB at 0000h-BFFFh, no mapper | three 16 KiB slots that never change; a ROM shorter than 16 KiB is repeated |
| RAM | 1 KiB at C000h, there again every 400h up to FFFFh | **8 KiB at C000h, there again at E000h: the Mark III's** (see below) |
| Ports 40h-7Fh | SN76489 (write) | as ggswan |
| Ports 80h-BFh | TMS9918A: even data, odd control (write) and status (read) | `gg.c`, under `GGSWAN_SG1000` |
| Ports C0h-FFh | even: joypad 1, and joypad 2's up and down; odd: the rest of joypad 2 | joypad 1 only |
| Pause | a non-maskable interrupt | `GG_KEY_START`, as smsswan |
| Video | 16 KiB of VRAM, 8 registers, 15 fixed colors and "transparent", four screen modes, 32 sprites of one color, four to a line | see below |
| Interrupts | the frame's (register 1 bit 5), no line interrupts, no line or column counters | the flag is set at the start of line 192 |

### The work RAM is the Mark III's

The recompiler reaches the work RAM in place, `C000h-DFFFh` at a fixed
distance in the internal RAM, and sends `E000h-FFFFh` to a helper: some
twenty places in `drc.c`, and the stack's own rules. A RAM of 1 KiB that
is there eight times would have meant changing all of them, for software
that does not exist as far as I know: every SG-1000 game also had to run
on the Mark III and the Master System, whose RAM is 8 KiB with one
mirror. And some later games (Taiwanese ones, sold with an "8kB RAM
adapter") need the 8 KiB at C000h. So: 8 KiB, the recompiler untouched.
`FFFCh-FFFFh` are plain RAM (no mapper).

Not there: the adapter's other kind (RAM at 2000h-3FFFh), and cartridges
with their own RAM at 8000h (The Castle, Othello): step 7.

### The TMS9918A in `core/`

- Control port: second byte with bit 7 set writes register `byte & 7`
  (8 registers); else it sets the address, bit 6 for writing, and reading
  ahead when it is clear. Data port: always VRAM (no color RAM). The
  platform is told of the bytes that change (`gg_platform_vram_write`).
- Status: bit 7 the frame flag, bit 6 with the number of the fifth sprite
  of a line in bits 0-4, bit 5 two sprites overlap. Reading clears it.
- `core/sg_vdp.c`: the 16 colors (`sg_palette`, 12 bits), the sprites as
  the screen has them (`sg_sprite`, `sg_sprite_row`), and
  `sg_sprite_status()`.

The sprite flags are worked out **once a frame**, at line 192, from the
sprite table as it is then (the chip sets them line after line): the same
thing for a game that writes the table during the vertical blank, as
they do. Not line by line: the lines of each sprite are counted in the
order of the table (the first four on a line are shown), then the pairs
whose rectangles meet are compared row by row. `sgtest` does the same the
long way, pixel by pixel, every frame, and counts the frames where the
two differ.

Known differences from the chip: bits 0-4 of the status read 1Fh when
there is no fifth sprite (the chip leaves the number of the last sprite
it looked at); the modes that mix M1, M2 and M3 are drawn as the first of
Graphics II, text, multicolor that is set.

## PC tools (`host/`)

```
make sg                                  # sgtest
./sgtest rom.sg 600 out "120:10,130:00" 60
make sgcheck                             # the four test ROMs
python3 mksgtest.py out.sg g1|g2|mc|text
```

`sgtest` draws the whole 256x192 picture line by line with a reference
renderer (Graphics I, Graphics II with the masks of registers 3 and 4,
multicolor, text; sprites 8x8 and 16x16, magnified, early clock, four to
a line) and writes PPM files. At the end it prints what the game used:
frames in each mode, sprites in the table and on a line, 16x16 and
magnified sprites, and the sprite status check. That list is what the
WonderSwan side needs to know of a game before it is tried there.

## The WonderSwan side: the plan

The WonderSwan draws tiles of 8x8 pixels with 16 colors (32 bytes each)
and sprites made of them. The TMS9918A's patterns are 1 bit a pixel with
their colors elsewhere, so nothing in its VRAM can be shown as it is
(the Game Gear's tiles can: ggswan's VRAM *is* the WonderSwan's tiles).

- **The TMS9918A's VRAM** (16 KiB) is kept as the game wrote it, outside
  the internal RAM: in the PSRAM bank after the ROM's, through the RAM
  window (segment 1000h), which nothing else uses while a game runs
  (to be checked in step 2: `psram_write` moves the window and puts it
  back).
- **One palette**: the 16 colors, for background and sprites. Color 0 is
  the WonderSwan's transparent one: the backdrop (register 7) shows
  through, as on the chip.
- **Background**: the name table is the WonderSwan's screen 1, one entry a
  character. A pattern with its colors becomes a tile **when a character
  on the screen first uses it** (a table from pattern to tile slot); a
  pattern or color byte written later marks its slot to be drawn again at
  the end of the frame. Graphics I has 256 patterns (colors: one byte for
  8 of them); Graphics II has 768 with 8 color bytes each, less when the
  masks of registers 3 and 4 make the thirds of the screen share them.
  Writing a name is then one table lookup and one word, whatever the
  mode, and patterns nobody shows cost nothing.
- **Sprites**: WonderSwan sprites, four of them for a 16x16 one, their
  tiles drawn in the sprite's color when its pattern, color or the bytes
  of the pattern change. Tiles 0-127: slot `4 * sprite + quarter`.
  Magnified sprites need 16 tiles each: counted first (`sgtest`), done if
  games use them.
- **The view**: 224x144 of the 256x192, moved with the Y buttons, as
  smsswan's.
- No software frame buffer, no line-by-line effects (the chip has none
  to offer: no scrolling, no line interrupt).

### Internal RAM

Step 3 changes nothing in ggswan's map:

| Where | ggswan, smsswan | sgswan, steps 3-4 |
|---|---|---|
| 0000h-3FFFh | C data, stack, screen maps, sprite tables | the same (one screen map) |
| 4000h-7FFFh | the VRAM = tiles 0-511 | tiles 0-127 sprites, 128-511 background slots (384) |
| 8000h-9FFFh | work RAM | work RAM |
| A000h-A5FFh | font (tiles 768-815) | font |
| A600h-BEFFh | the recompiler's translation buffer | the same |
| C400h-CFFFh, F200h-FDFFh | deferred VRAM writes | free |
| D000h-DFFFh | L0 cache | the same |
| E000h-F1FFh | decoder, sound, ROM path, first KiB of the ROM, flag tables | the same |

384 slots are enough for Graphics I and for most Graphics II screens,
not for a full-screen picture: the view shows up to 29 x 19 = 551
characters, each with its own pattern. Step 5 moves the translation
buffer to C000h-D8FFh and the L0 cache, halved, to F200h-F9FFh (both
addresses are constants of the build), which frees A600h-BEFFh: tiles
816-1015, 584 slots in all. When the slots run out, the ones no
character on the screen uses are taken back.

### Gates (from the study this plan started from)

1. `PLUG_GG.BIN` and `PLUG_SMS.BIN` do not change with the SG-1000 work,
   but for the patch number: compared byte by byte with the binaries of
   the patch before, built with the same number.
2. Every step on the WonderSwan side is compared with `sgtest`'s picture
   in a simulator before it goes to the device.
3. The recompiler is compared with the interpreter on SG-1000 ROMs
   (`drcsys.py`) before step 3.
4. The target is the Game Gear's: a frame in 51,300 V30MZ cycles.
