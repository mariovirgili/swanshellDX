# sgswan: the SG-1000 plugin

`PLUG_SG.BIN` is built from the ggswan sources with `-DGGSWAN_SG1000`
(`make -f Makefile.ggswan SG=1`; the main build makes it with the other
two), the way `PLUG_SMS.BIN` is built with `-DGGSWAN_SMS`. The menu
starts it for `.sg` files. How to use it is in `README.md`; this file is
how it is made, what was measured, and what is left.

**Where it stands (patch 143):** games run, with the recompiler, sound,
the background and the sprites. Tried in the PC tools only (the picture
against a reference renderer, the recompiler against the interpreter, the
device build in an x86 emulator): **not yet on a WonderSwan nor in
nileswan-medem**.

## The machine

| | SG-1000 | here |
|---|---|---|
| CPU | Z80, 3.58 MHz | the same core and recompiler as ggswan |
| ROM | 8 to 48 KiB at 0000h-BFFFh, no mapper | three 16 KiB slots that never change, FFh after a shorter ROM |
| RAM | 1 KiB at C000h, there again every 400h up to FFFFh | **8 KiB at C000h, there again at E000h: the Mark III's** (see below) |
| Ports 40h-7Fh | SN76489 (write) | as ggswan |
| Ports 80h-BFh | TMS9918A: even data, odd control (write) and status (read) | `gg.c`, under `GGSWAN_SG1000` |
| Ports C0h-FFh | even: joypad 1, and joypad 2's up and down; odd: the rest of joypad 2 | joypad 1 only |
| Pause | a non-maskable interrupt | `GG_KEY_START`, as smsswan |
| Video | 16 KiB of VRAM, 8 registers, 15 fixed colors and "transparent", four screen modes, 32 sprites of one color, four to a line | see below |
| Interrupts | the frame's (register 1 bit 5), no line interrupts, no line or column counters | the flag is set at the start of line 192 |

### Memory

- **The work RAM is the Mark III's**, 8 KiB with one mirror, not 1 KiB
  repeated eight times. The recompiler reaches `C000h-DFFFh` in place and
  sends `E000h-FFFFh` to a helper, in some twenty places of `drc.c`; every
  SG-1000 game also had to run on the Mark III, and the games that use
  the stack (all nine tried) keep it in `C000h-C400h`. `FFFCh-FFFFh` are
  plain RAM (no mapper).
- **RAM at 8000h-BFFFh** after a ROM of 32 KiB or less: where cartridges
  with their own RAM have it (The Castle, 8 KiB). It is the rest of the
  ROM's PSRAM bank, which the recompiler reads as it reads the ROM.
- **RAM at 2000h-3FFFh** when that part of the ROM is all FFh: the "8kB
  RAM adapter" of some Taiwanese games (TwinBee, Bomberman Special), which
  have nothing else there. A game with no use for it never looks.

### The TMS9918A in `core/`

- Control port: second byte with bit 7 set writes register `byte & 7`
  (8 registers); else it sets the address, bit 6 for writing, and reading
  ahead when it is clear. Data port: always VRAM (no color RAM). The
  platform is told of the bytes that change (`gg_platform_vram_write`).
- Status: bit 7 the frame flag, bit 6 with the number of the fifth sprite
  of a line in bits 0-4, bit 5 two sprites overlap. Reading clears it.
- `core/sg_vdp.c`: the 16 colors (`sg_palette`, 12 bits), the sprites as
  the screen has them (`sg_sprite`, `sg_sprite_row`), and
  `sg_sprite_status()`.

The sprite flags are worked out **once a frame**, at line 192, from the
sprite table as it is then (the chip sets them line after line): the same
thing for a game that writes the table during the vertical blank, as
they do. It runs on every frame of every game, so it does as little as it
can: the table copied once, the sprites that are on no line left out, the
lines counted only with more than four sprites (a count up where each
starts, down where it ends), and only the pairs whose rectangles meet
compared row by row. `sgtest` does the same the long way, pixel by pixel,
every frame, and counts the frames where the two differ: none in 3600
frames of each of the nine games.

Known differences from the chip: bits 0-4 of the status read 1Fh when
there is no fifth sprite (the chip leaves the number of the last sprite
it looked at); the modes that mix M1, M2 and M3 are drawn as the first of
Graphics II, text, multicolor that is set.

## The screen on the WonderSwan (`ws/sg_video.inc`)

The WonderSwan draws tiles of 8x8 pixels with 16 colors (32 bytes each)
and sprites made of them. The TMS9918A's patterns are 1 bit a pixel with
their colors elsewhere, so nothing in its VRAM can be shown as it is
(the Game Gear's tiles can: ggswan's VRAM *is* the WonderSwan's tiles).
`main.c` includes `sg_video.inc` in place of its Game Gear video.

- **The VRAM** (16 KiB) is kept as the game wrote it, in the last 16 KiB
  of the ROM's PSRAM bank (the ROM is 48 KiB at most), where the RAM
  window is anyway for the ROM's third slot: `gg_vram` is `1000h:C000h`.
  A write sets a byte for its 16 bytes of VRAM and one for its 512
  (`SG_DIRTY_ADDR`, `SG_PAGE_ADDR`): nothing else until the frame ends.
- **One palette**: the 16 colors, for background (palette 0) and sprites
  (palette 8). Color 0 is the WonderSwan's transparent one: the backdrop
  (register 7) shows through, as on the chip.
- **Background**: screen 1, one entry a character, scrolled to the view.
  A pattern with its colors becomes a tile **when a character in the view
  first shows it**. A *key* says which pattern and which colors: the
  character's number, with its third of the screen in Graphics II (under
  the masks of registers 3 and 4), with its row in multicolor. A key has a
  *slot*, a WonderSwan tile, while characters in the view show it; a slot
  nobody shows waits in a ring with its tile and is taken for another key
  only when its turn comes, so a game that scrolls by rewriting names
  finds most of its tiles still there. At the end of the frame the slots
  whose pattern or color bytes were written are drawn again, then the
  characters whose names were written get their slots. 558 slots: tiles
  160-511 and 816-1021.
- **Sprites**: WonderSwan sprites, of tiles drawn in the sprite's color,
  one set for each pattern and color on the screen (a *kind*: 1 tile for
  an 8x8 sprite, 4 for 16x16, four times as many magnified), in tiles
  0-159. A kind is drawn again when its pattern bytes are written.
- **The view**: 224x144 of the 256x192, moved with the Y buttons. When
  it moves to other characters, the ones that left give their slots back.
- The slots' tables are in the PSRAM bank after the ROM's (the internal
  RAM has no room for them), reached by moving the RAM window there
  inside `video_present`; the VRAM is then read through the ROM's window.

What the nine games use (`sgtest`, 3000-3600 frames with keys): Graphics
II all of them, never Graphics I, multicolor or text; up to 16 sprites on
the picture of up to 16 kinds; magnified sprites in three (Bank Panic,
Bomberman Special, Zoom 909); 74 to 228 characters with their own pattern
in the view in most, 536 in Bomberman Special's title and 551 in The
Castle (every room a picture).

Not done: **text mode** (40 columns of 6 pixels do not fall on tiles: the
backdrop is shown); **the four sprites to a line** (the WonderSwan shows
them all: no flicker, and a game that hides sprites behind four others
shows them); the tiles are written while the WonderSwan draws (a frame
may show a tile half old, half new).

### Internal RAM

| Where | ggswan, smsswan | sgswan |
|---|---|---|
| 0000h-3FFFh | C data, stack, screen maps, sprite tables | the same |
| 4000h-7FFFh | the VRAM = tiles 0-511 | tiles 0-159 sprites, 160-511 background slots |
| 8000h-9FFFh | work RAM | work RAM |
| A000h-A5FFh | font (tiles 768-815) | font |
| A600h-BEFFh | the recompiler's translation buffer | background slots (tiles 816-1021) |
| C000h-CFFFh | (C400h-CFFFh: deferred VRAM writes) | the translation buffer (to D8FFh) |
| D000h-DFFFh | L0 cache, 512 entries | the buffer's end; D900h-D920h: written pages of VRAM, "anything written" |
| E000h-F1FFh | decoder, sound, ROM path, first KiB of the ROM, flag tables | the same |
| F200h-F9FFh | deferred VRAM writes | L0 cache, 256 entries (half) |
| FA00h-FDFFh | | written 16-byte pieces of VRAM |

PSRAM: bank 0 the ROM (0000h-BFFFh; RAM where it is shorter, see above)
and the VRAM (C000h-FFFFh); bank 1 the slots' tables; the code cache
above (checked at the start).

## The recompiler

The Game Gear's video routines (VRAM writes straight into tiles, the
name table, the palette, runs of OUTI) are for a VDP whose VRAM is the
WonderSwan's tiles: off in this build (`drc_rt.c`, after the stubs are
written). In their place (`drc.c`, `drc_emit_sg_stubs`, `sg_block_io`):

- the data port out and in, the status, the control port's address
  bytes: short routines called from the block (a register write still
  goes to C);
- INI, IND, OUTI, OUTD (runs of them) and INIR, OTIR with the data
  port: a loop around those routines, INI's bytes to the work RAM in
  place; another port, or INI to somewhere else: the interpreter.

The line routine at the blocks' exits is off (no line interrupts). No
mapper routines.

Two things found on the way, wrong before this build existed:

- LDIR and LDDR to somewhere outside the work RAM: the interpreter's
  step does all of the instruction, and the block then went back to the
  instruction, with BC = 0: 64 KiB more, through all of the memory. The
  Castle fills its cartridge RAM this way. Fixed in this build; the Game
  Gear's and Master System's have it too (the patch after 143).
- An interpreted step puts the interrupt request back as it was before:
  an instruction that changes it (a register write that enables the
  frame interrupt with the flag set, a status read) loses that. Block
  output to the control port does not go that way here; `IN r,(C)` from a
  port not known when translating still does, in all three builds.


## PC tools (`host/`)

```
make sg            # sgtest, wssim_sg, libdrcsys_sg.so
make sgcheck       # the four test ROMs of mksgtest.py through sgtest
./sgtest rom.sg 600 out "120:10,130:00" 60
./wssim_sg rom.sg 600 out "120:10,130:00" 60
python3 drcsys.py ./libdrcsys_sg.so rom.sg 600 out "" 0
python3 wsrun.py ../../../build/sgswan.elf rom.sg 600 100
```

- `sgtest`: the machine with the reference renderer (`sg_ref.h`), the
  whole 256x192 picture line by line; at the end what the game used
  (modes, sprites, kinds, characters with their own pattern, bytes
  written a frame), and the sprite status check.
- `wssim_sg`: `sg_video.inc` on the PC; the WonderSwan screen it programs
  next to the reference's view, and how many pixels differ.
  `GGSWAN_PAN=x,y` sets the view, `GGSWAN_PANMOVE=1` moves it all the
  time.
- `libdrcsys_sg.so` with `drcsys.py`: the recompiler against the
  interpreter. (A game that takes random numbers from R parts from the
  interpreter at the first one: Gulkave, at frame 325. And Zoom 909
  from the helper build at frame 863: its OTIR to the PSG is done in C,
  without the interpreter's count of R.) Built with
  `-DGGSWAN_SG_NOSTUBS` it sends every port to the helper: the reference
  the port routines are compared with (`--ref-lib`, `--nolinks`).
- `wsrun.py` with `WSRUN_SHOT=prefix` writes the device build's internal
  RAM and ports every so many frames; `wsshot.py` draws the WonderSwan
  screen they make (the device build has far pointers and a window
  moved back and forth that the PC builds do not). `WSRUN_STUCK=cycles`
  stops at a frame that takes more than that and says where it is (how
  The Castle's LDIR was found: `wssim_sg` has no recompiler, and the
  recompiler's tests were compared with each other); `WSRUN_STACK=addr`
  says how far down the stack went.
