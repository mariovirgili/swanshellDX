## Using it

Copy `PLUG_SF.BIN` to `/NILESWAN/`, and **a disk that has Disk BASIC on
it to `/NILESWAN/SF7000.SF`** (the system disk: a copy of any disk image
that starts by itself, such as The Complete Arcade Pack Collection; Disk
BASIC is Sega's and is not in the plugin). A `.sf` file chosen in the
menu goes in the drive:

- a disk with Disk BASIC on it (`SYS: disk BASIC` at its start) starts;
- a disk with a system of its own that is made to be started from Disk
  BASIC with `BOOT` (`SYS:` and another name: Kamikaze's is `BASIC LEVEL
  IIIB+KAMIKAZE`, and its directory says so) is started from the system
  disk, and `BOOT` is typed for it six seconds after Disk BASIC is
  loaded (patch 150; started by itself, Kamikaze's screen comes out
  mirrored, on the PC with the interpreter too);
- any other is started from the system disk: Disk BASIC comes up, and the
  disk chosen is in the drive when it has (`FILES` lists it, `RUN
  "name"` runs a program of it);
- **B held while the plugin starts**: from the system disk too, whatever
  the disk (nothing is typed then).

| Keys | Function |
|---|---|
| X1-X4, B, A | The joypad: D-pad, button 1, button 2 |
| START | **The keyboard**, on and off (when START is let go): the top five rows of the screen |
| Y1 (Y up), Y3 (Y down), Y4 (Y left), Y2 (Y right) | Move the view over the picture, as sgswan's |
| START + Y1 (Y up), held for a second | Back to the menu |
| START + Y3 (Y down) | The whole picture squeezed, on and off (as sgswan's; not in text mode) |
| START + Y2 (Y right) | Four sprites to a line, on and off (as sgswan's) |
| B held at the start | Start from the system disk (see above) |

With the keyboard on the screen: X1-X4 choose a key, **A** presses it (for
as long as A is held), **B** is CR. The last row: `SH` SHIFT for the next
key, `BK` BREAK, `DL` INS/DEL, `SP` space, `CR`, then lines typed for you:
`FI` (`FILES` and CR), `LO` (`LOAD "`), `RU` (`RUN` and CR), `BO` (`BOOT`
and CR). The joypad is not read while the keyboard is there.

What the program writes to the disk stays in memory and is lost when the
plugin is left.

## The machine

An SF-7000 is a box under an SC-3000 (an SG-1000 with a keyboard): 64 KiB
of RAM, a 3" disk drive on a uPD765, an 8 KiB ROM (the IPL) that starts
the disk, a printer port and an RS-232C one. Its programs are on disks of
40 tracks of 16 sectors of 256 bytes, one side: 163,840 bytes, which is
what a `.sf` file is (track by track, the sectors in order).

| Part | Here |
|---|---|
| CPU, TMS9918A, SN76489 | the SG-1000's (`gg.c`, `sg_vdp.c`): the same ports, the frame interrupt |
| Memory | `gg.c` (`GGSWAN_SF7000`): `sf_ram`, 64 KiB; `sf_ipl` read at 0000h-3FFFh (8 KiB, twice) while the 8255's PC6 is low. A write there goes to the RAM behind: the disk's loader fills 0000h up that way, then sets PC6 and jumps to what it loaded |
| Ports C0h-DFh | the SC-3000's 8255 (`sf7000.c`): port C bits 0-2 choose a row of the keyboard, A and B read its 12 columns (0 = pressed); row 7 is the joypads, and is what is read with port C never written: an SG-1000 game finds its joypad |
| Ports E0h-E3h | the uPD765: E0h the main status, E1h the data |
| Ports E4h-E7h | the SF-7000's 8255: A in (bit 0 the uPD765's INT, bit 2 the drive's INDEX), C out (0 /INUSE, 1 /MOTOR ON, 2 TC, 3 the uPD765's RESET, 6 /ROM SEL), E7h the mode or one bit of C |
| Ports E8h-EBh | the 8251: nothing on its line |
| Keyboard | `sf_keys[7]`, a bit for each key of the matrix (`sf_key_set`, `sf_char_key` for a character: with SHIFT where it needs it). The RESET key is the non-maskable interrupt: `GG_KEY_START` |

### The uPD765

As its programs see it, with no time in it: a command is done when its
last byte is written, a seek at once, and in a transfer the next byte is
always there. The chip's phases are kept (command bytes, then the
sector's bytes through the data port with EXM set in the status, then the
result bytes), with its interrupt line, TC from the 8255 to end a
transfer, the "end of cylinder" error when a transfer runs past the last
sector with no TC, "no data" for a sector that is not on the track the
head is on, "not ready" with no disk. Commands: SPECIFY, RECALIBRATE,
SEEK, SENSE INTERRUPT STATUS, SENSE DRIVE STATUS, READ ID, READ DATA,
WRITE DATA, FORMAT A TRACK; anything else is "invalid" (80h).

What Disk BASIC's own driver does (it does not use the IPL after the
start), found by reading it (3620h-3880h of the system on the disk):
- it reads 256 bytes polling the status for each (`IN A,(E0h)` / `RLCA` /
  `JR NC` / `AND 40h` / `RET Z` / `INI`), then pulses TC (E7h: 05h, 04h)
  and waits for the interrupt line before the result bytes;
- before every command it sends SENSE INTERRUPT STATUS for as long as the
  interrupt line is high;
- **each time it starts the motor it measures the disk's speed**: it waits
  for the index hole twice and counts 51-cycle loops between: 12,634 to
  15,441 are accepted, a turn of 180 to 220 ms. So the drive's INDEX line
  has to come once every 716,000 CPU cycles (200 ms), for 14,000, while
  the motor is on: `sf_index`, from the cycles the machine has run
  (`sf_clock`). Before that it waits a second for the motor (a loop).

### The IPL: not Sega's

The SF-7000's ROM is Sega's and is not in these sources. The plugin has
its own (`host/mksfipl.py` writes `core/sf_ipl.h`: 2,408 bytes, 616 of
Z80 code in a small assembler of its own and a font), made from what the
IPL is documented to do for a disk and none of its code. It is a program the emulator runs,
talking to the emulated uPD765 through the ports as any other would:

| Address | What |
|---|---|
| 0000h | the start: the 8255s, the PSG silent; on a first start the VRAM and the RAM filled as the IPL's self test leaves them; the VDP in text mode with a clear screen; track 0 sector 1 to FF00h and, if it starts with `SYS:`, a jump to FF20h (the disk's loader) |
| 0008h | the drive on, SPECIFY, RECALIBRATE (carry: no disk) |
| 0010h, 0018h | read, write the sector B (1-16) of track C (0-39) at DE (carry: an error); the other registers kept |
| 0020h, 0028h | format a disk, the copy program: not there (carry) |
| 0030h | the start, never as a first one |

Three things of the real one are kept because programs turned out to
count on them:
- **the font it leaves in the VRAM** (1800h: characters 20h-FFh from
  1900h). Disk BASIC loads no font for its text screen: with none there
  its prompt is an empty green screen. The one here is not the
  SC-3000's: 20h-7Fh are the plain 5x7 dot matrix letters of terminals
  and LCD modules; 80h-FFh (lines, blocks, card suits, accented and Greek
  letters on an SC-3000) are drawn from the list of what each one is,
  the accented letters as the plain letter;
- **FC52h = 55h means "the self test was passed"**, and with it there the
  start leaves the memory alone. Disk BASIC's `BOOT` command comes this
  way, and Kamikaze's disk is made to be started with it: its loader
  leaves the VDP as it finds it, and the game draws on the graphics
  screen Disk BASIC had set up. Started cold, its screen is black;
- on a first start the IPL's self test writes all of the VRAM and the
  RAM: every byte of VRAM is left the sum of the two bytes of (4000h -
  its address), every byte of RAM the sum of the two bytes of its
  address. The same is written here (no test), so that a program finds
  what it would have found.

Not there: the self test itself, the messages (a disk that does not
start leaves an empty screen), the disk's speed test (the
disk here is at speed at once), the copy and format program.

`SF_IPL=file` makes `sftest` use another IPL of 8,192 bytes instead (the
SF-7000's own, for whoever has it: not tried).

## Disks that need Disk BASIC

Only a disk with a system on it starts by itself (`SYS:` at its start,
and a loader at 20h that the IPL jumps to). Of the three here:

| Disk | How it runs |
|---|---|
| The Complete Arcade Pack Collection | starts: Disk BASIC 1.0p, then `LOAD "ASTRO.BAS"`, `RUN` |
| Kamikaze | has `SYS:` but must be started from Disk BASIC with `BOOT` (its directory says so, in French): Disk BASIC from another disk, this one in the drive, `BOOT` |
| Poseidon Wars + Space Panic + Rambo | no system: Disk BASIC from another disk, this one in the drive, `RUN "POSEIDON.BAT"` |

So the plugin will need a second disk: a system disk to start from, and
the disk asked for put in the drive when its loader has finished. On the
PC: `SF_SWAP="0:other.sf"` (when the first disk's loader gives the memory
to what it loaded), or `SF_SWAP="frame:other.sf"`.

## PC tools

```
cd src/ggswan/host
make sftest sf_unit
./sf_unit disk.sf                       # the parts through their ports: 56 checks
SF_TYPE='500:FILES\n' ./sftest disk.sf 900 out "" 0
make sfcheck DISK=disk.sf               # both
python3 mksfipl.py ../core/sf_ipl.h     # the built-in IPL, after changing it
```

`sftest disk.sf frames out_prefix [joypad keys] [picture every n frames]`
runs the machine with the interpreter and the SG-1000's reference
renderer, and prints the text screen at the end. `SF_TYPE='frame:text|
frame:text'` types on the keyboard (a key every 8 frames; `\n` is CR,
`\b` BREAK), `SF_SCREEN=1` prints the text screen with every picture,
`SF_TRACE=1` says when the IPL comes and goes at 0000h, `SF_SWAP` changes
the disk, `SF_VRAM=file` saves the VRAM (and the RAM in `sf_ram.bin`).

`sf_unit` (no program running): a write under the IPL goes to the RAM and
is read after PC6 is set; the 8255's mode word and bit set/reset (the
loader's 03h and 0Dh to E7h); the keyboard's rows, ENTER, SHIFT, the
joypad in row 7; the uPD765's phases, status bits and interrupt line;
sectors read through it against the file (track 0 sector 1, the
directory at track 20, the last sector); sector 0, sector 17, the other
side, a size of 512, the wrong track, track 40: no data, and the chip
takes commands again; two sectors in one command and the end of the
cylinder; TC in the middle of a sector; a sector written and read back; a
protected disk; a track formatted; no disk; the index hole five times in
59 frames, 61 lines each.

## The WonderSwan side (patch 148)

- **The memory.** PSRAM bank 0 through the RAM window is the Z80's 64
  KiB, Z80 address = offset; bank 1 holds the tiles' tables of
  `sg_video.inc`, the two bitmaps below and the VRAM (at C000h, read
  through the first ROM window, written by moving the RAM window); banks
  2-4 the disk, 5-7 the system disk; the code banks after them.
- **The recompiler, "flat"** (`FLAT` in `drc.c`, compiled only with
  `-DGGSWAN_SF7000`: the other plugins' translator gives the same bytes as
  before, checked with `drcsys.py --same-code`). ES is the memory's
  segment wherever translated code runs; a read is `ES:[address]`, a write
  too after a look at the code map (a byte for each 16 of the memory, in
  the internal RAM: is there translated code there?), and then the
  helper, which knows byte by byte (a bitmap in PSRAM) and throws the
  blocks away if code was written. The stack is where the program puts
  it, not looked at.
- **Code that writes over code.** Disk BASIC wipes its own start-up, and
  Astro's machine code keeps its variables in its instructions (`LD (lab
  + 1),A`): every such write threw all the blocks away (9,590 times in
  5,000 frames). Now a byte that was written while it was translated code
  is remembered (a second bitmap); an instruction with such a byte is run
  by the interpreter where it is, in its block, and a write to it costs a
  helper's call. 8-12 times in 5,000 frames.
- **The IPL's long parts are not Z80 code on the WonderSwan.** The
  built-in IPL asks the machine for them through port ECh (`sf_service`
  in `sf7000.c`: the memory and VRAM filled, the font and the clear
  screen, a sector read or written), because the interpreter runs the
  IPL (it is ROM over RAM, and gone in a few seconds) and is 30 to 60
  times slower than the SF-7000: the same IPL as plain Z80 code
  (`SF_IPL_PLAIN=1` in `sftest`) leaves the same memory but for 12 bytes
  of its own stack.
- **Text mode** in `sg_video.inc` (also for sgswan): 40 columns of 6
  pixels, each WonderSwan tile two halves of characters, a tile for each
  place of the view (29 x 19).
- **The disk's speed.** `IN A,(E4h)` (the index hole, the uPD765's
  interrupt line) is read from a value kept while it cannot change
  (`sf_port_a_steady`): Disk BASIC's speed test reads it some 14,000
  times a turn of the disk.

### Measured (the device build in `wsrun.py`, cycles estimated)

| What | Cycles a frame | Against the SF-7000 |
|---|---|---|
| The start, to the prompt | about 300 frames | about 5 seconds of IPL and loader, then Disk BASIC's own start |
| At the `Ready` prompt | 103 k | half speed: half of it is a delay loop of the keyboard scan (`DEC C / JP NZ` at 5FDAh, 123 turns between rows) |
| `FILES` | up to 420 k | the uPD765's bytes one by one through the helper: slow |

Full speed is 51 k cycles a frame.

## Known limits

- Not tried on a WonderSwan nor in nileswan-medem.
- Half speed at Disk BASIC's prompt. A try at doing its delay loops in
  one go (as `DJNZ $` is in the other plugins) was right in `drcsys.py`
  against the interpreter and stopped the device build in `wsrun.py` at
  the disk's speed test (Z80 374Fh, the frame never ending): taken out,
  to be looked at again.
- Slow where a program reads the disk (a helper's call for every byte of
  a sector) and wherever it runs in the interpreter.
- 60 frames a second: these disks are from New Zealand and France, whose
  machines drew 50, with 313 lines. The programs run a fifth faster than
  they did (when the plugin keeps up).
- The disk is not written back to the card.
- The IPL shows no messages (the SF-7000's says `disk not ready` and
  `set disk and hit space key`, and the name after `SYS:`): a disk that
  does not start leaves an empty screen.
- No RESET key, no printer, nothing on the serial port, no second joypad.
